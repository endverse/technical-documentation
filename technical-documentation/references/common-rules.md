# Common rules

- Identify the primary reader and outcome before drafting. Split role-specific material by default. Describe the reader's own responsibilities and next actions; do not explain what other roles do not need to do.
- Classify each key statement by an objective test:
  - **verified fact** — reproduced by a re-runnable command, test, or direct observation whose output you can cite; not merely asserted.
  - **sourced fact** — stated by an external authority (vendor doc, ticket, spec) you can cite by link or ID; a sourced fact is never silently upgraded to verified (e.g. “官方文档说支持” stays sourced, not “已验证”).
  - **confirmed business decision** — a recorded decision with a named owner.
  A key conclusion must map to one tagged evidence item. If a required element (owner, approval/application path, acceptance criterion, value) is unknown or evidence conflicts, do not fill it with vague on-the-spot-confirmation filler (e.g. “若不存在则现场确认”); mark it a gap and pause to offer stop / record-as-pending / record-as-blocker. Do not claim a document is complete or executable while such gaps remain.
- Use one forward reading path: context and conditions before decisions or action. Each section answers one question. Define terms before later use and use one canonical term per concept.
- Keep concepts, procedures, reference facts, troubleshooting, incident analysis, and retrospective learning separate. Link to a source of truth instead of duplicating it.
- Keep final effective paths. Remove failed attempts, transcripts, parenthetical asides, vague headings, repeated explanations, and any text whose removal would not make the reader misunderstand or fail.
- **Write only reader-needed information.** In a formal document, delete content that explains how the document was drafted, selected, split, compared, replaced, or intentionally shortened — including author-side exclusions, former-document comparisons, replacement relationships, and lists of deliberately omitted roles, products, features, or subjects. Also delete Agent self-commentary, tool activity, completion notices, and invitations for more work. Give the reader the applicable action, condition, responsibility, or link instead. This is a content-purpose rule, not a banned-word list: apply it regardless of domain, product, role, or language.
- Keep a boundary statement only when it changes how the reader interprets the result or safely completes work. For example, a test report may state untested acceptance criteria and their effect on the conclusion; an architecture design may state system and interface boundaries; an operations guide may state a required permission, version, or recovery condition. State the relevant fact and its effect, not why the author chose not to write something.
- Keep a negative statement only when omitting it would create a concrete safety, authorization, compatibility, data-loss, or irreversible-operation risk. State the required positive action and resulting path where possible; make the prohibition short and operational. For example: “凭据通过工单提交；不得写入 Git。” Do not use a negative statement merely to describe scope, history, alternatives, or an excluded audience.
- Write Chinese unless asked otherwise. Keep commands, identifiers, paths, fields, APIs, and errors verbatim in code style. Use direct verbs and observable statements; avoid vague phrases such as “应该”, “一般来说”, and “相关配置即可”.
- Use diagrams for relationships or flows, tables for comparison/conditions/responsibility/results, code blocks for copyable commands, and screenshots only when visuals clarify location or evidence.
- Never include passwords, tokens, private keys, or other **credentials** (secret values that grant access). A credential value taken from input material is never reproduced verbatim anywhere in the deliverable — not in security warnings, "rotate this" notes, quotes, or examples; refer to it only by a generic placeholder and describe it by type and source, not value. Use secure-transfer instructions (e.g. deliver via ticket, not in the document) instead of the value. This does not override the verbatim rule for **identifiers** (command names, API fields, paths, error strings, non-secret resource names): a credential is a secret that authenticates; an identifier names a thing and carries no secret. When unsure whether a value is secret, treat it as a credential. Include an internal address, endpoint, repository, or cluster identifier only when the target reader needs it, the user has supplied or approved it, and the document's intended access scope is appropriate; otherwise use a placeholder or ask.
- For any document whose correctness decays over time — operations-runbook, deployment-plan, test-report, handover-checklist, service-onboarding — state version/environment, date, owner, and last-verification time in the document. Use clear direct links, not “见前文” or “见相关文档”.
- Admission and reading logic are separate. [Claim sheet](claim-sheet.md) decides what may enter. [Presentation](presentation.md) decides order and connective sentences. Do not apply the procedure pruning test to judgment documents.
