# Document splitting and navigation

Split when readers, goals, ownership/update cadence/access scope, or independently executable workflows differ. Split dense parameter, interface, error-code, or command references away from the main path.

Recommend splitting when shared material repeats three or more times, five or more independent tasks exist, maintainers differ, or the table of contents no longer gives a clear start. Do not split one short continuous flow or create one-sentence child pages.

After splitting, create an entry document with purpose, readers, scope, reading path, child purposes, and shared prerequisites. Maintain shared content once. Cross-file procedures must name and link to the next document. Before creating a multi-file set or structurally splitting an existing document, show the tree, reader, purpose, and order; wait for confirmation.
